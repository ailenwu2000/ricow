# 017 实施计划

## 一、决策

| # | 决策 | 理由 |
|:--|:--|:--|
| D1 | 修在**引擎侧**(清理按市场分支用 `spot_position_of`), 而非改 `BnSpotExchange::get_position` 的现货语义 | `get_position` 的"现货无合约持仓"表述在其自身语境成立; 引擎侧本就有 `spot_position_of`(成交后刷新在用), 复用同源可保证清理/刷新/残留三处口径一致 |
| D2 | 现货刷新**持仓 + 现金**成对出现 | 策略按 equity 定目标; 只刷一半就会算错(这正是 B 的根因) |
| D3 | 下单后有成交 → 立刻 `refresh_positions` | 成交回写是异步的; 主动拉一次即可闭合窗口, 且不引入"乐观记账"(避免与用户流重复计数) |
| D4 | 不加 mock Exchange 单测 | 宪法: 交易流程禁 mock 替身; 本组缺陷均为**接线/时序**问题, 真实 demo 链路是唯一有效验证(已实跑) |

## 二、改动清单

| 文件 | 改动 |
|:--|:--|
| `crates/locus_engine/src/command.rs` | 清理与残留复查的持仓源按市场分支; `refresh_positions` 现货分支补刷 base/quote 余额; 实盘下单批次后按 `any_filled` 触发刷新 |
| 文档 | `architecture.md` / `testnet.md` / `roadmap.md` / P4 runbook / 本档案 |

## 三、风险

| # | 风险 | 处置 |
|:--|:--|:--|
| R1 | 每次成交多几次 REST 查询(余额) | 仅在成交/下单批次后触发; 现货 `get_account` 权重低; 优先正确性 |
| R2 | 刷新失败导致快照仍陈旧 | 失败只 warn + 下一 tick 继续收敛; 不把失败当成"无持仓"(FR-005) |
| R3 | 误改合约路径 | 合约分支保持原样(定向持仓 + 强平告警), 现货分支独立 |

## 四、验收动作

3. 对照修复前/后统计(`提交订单` / `拒单` / `成交` / 平仓单 / 残留)与交易所账户状态。
4. 文档同步。
