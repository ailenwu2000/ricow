# 027 功能规格: 停机动作对"不存在的策略名"误报成功

**功能目录**: `specs/changes/027-stop-unknown-instance`

**创建日期**: 2026-09-20

**状态**: 草稿

**输入**: 用户描述: "先验证cli所有功能。测试：策略生成，回测，dryrun，demo运行，实盘运行，管理策略。" —— 验收过程中发现停机动作的假成功缺陷。

## 一、为什么

本轮 CLI 全功能验收(策略生成 / 回测 / Dry Run / demo / 实盘门禁 / 管理策略)中确认: **`ricow stop` 对任何名字都回"已停止"**。

实测(2026-09-20, `ricow 0.7.0`):

```
> .\target\debug\ricow.exe stop no-such-strategy
策略 no-such-strategy 已停止 (用时 0ms)
该策略未在运行 (无需停止)                          exit=0
```

`no-such-strategy` 既没有 `strategies/no-such-strategy.toml`, 台账里也没有任何记录 —— 这个名字在本机**不存在**。CLI 仍然回退出码 0 并打印"已停止"。

同一个根因还污染 `restart`(它的第一步就是 stop):

```
> .\target\debug\ricow.exe restart no-such-strategy
策略 no-such-strategy 已停止 (用时 0ms)          ← 假成功
该策略未在运行 (无需停止)                          ← 假成功
错误: invalid argument: 读取策略 no-such-strategy 失败: 系统找不到指定的文件。 (os error 2)
                                                    exit=1
```

前两行是假成功, 第三行才报错 —— 用户看到的前两行与最终失败互相矛盾。

**为什么这在金融交易系统里严重**: 停机是风险动作里最需要确定性的一类。用户打错一个字母(或 AI 传错名字), 得到的回执是"已停止 / exit=0", 用户据此认为风险已解除 —— 而真正该停的策略仍在跑。这是"假阴性回执", 比明确报错危险得多。此前的用户质疑(「没有可停止的对象 —— 它已经是停着的, 所以我这回什么都没登记, 也没有动作被消耗」)指向的正是这条通道的可信度。

**第二处问题(同源, 文案自相矛盾)**: 一个**真实存在、确实没在跑**的实例, 停机回执的头一行仍说"策略 shannon-grid-eth **已停止** (用时 0ms)", 下一行才说"该策略**未在运行** (无需停止)"。同一份回执里"已停止"与"未在运行"互相打架 —— 026 已经改了后半句(不再说"没有可停止的对象"), 但前半句的"已停止"头衔留在原地。

**根因(已定位)**: 停机内核在拿不到子进程句柄时, 直接构造一份 `exited=true` / `exit_code=None` 的**成功**报告返回, 不区分"这个名字根本不存在"与"名字存在但没在跑"。见 [server.rs](../../../crates/ricow/src/supervisor/server.rs#L212-L224); CLI 侧则无条件据 `exited=true` 打印"已停止", 见 [ctrl.rs](../../../crates/ricow/src/commands/ctrl.rs#L229-L254)。

**对照: 同仓库其余名字入口早有正确口径**, 缺口只在停机路径:

| 入口 | 未知名字时的行为(实测) | 判定 |
| --- | --- | --- |
| `ricow status X` | `错误: invalid argument: 未找到策略或实例 X (strategies/X.toml 不存在, 也无实例台账)` exit=1 | 正确 |
| `ricow info X` | 同上, 逐字一致 | 正确 |
| `ricow logs X` | `错误: invalid argument: 日志不存在: …\logs\X.log (该策略尚未启动过?)` exit=1 | 正确 |
| AI 工具 `stop_*` | `没有名为 X 的实例(既未在运行, 也没有退出台账); 可用 instance_status 确认现状` | 正确(且更严格) |
| **`ricow stop X`** | **`策略 X 已停止` exit=0** | **缺陷** |
| **`ricow restart X`** | **先假成功, 再报错** | **缺陷** |

**本次主旨**: 让停机路径的名字判定与其余入口**同口径**, 且让回执文案与事实一致 —— **不改任何停机执行语义**(停机指令下发 / 等待退出 / 超时如实报告 / 清理提示 / `--close-all` 行为一行不动)。

## 二、范围

**做**:

- **停机前置存在性判定**: `ricow stop <name>` 在名字**完全不存在**时, 以非零退出码明确报错, 回执中**不得**出现"已停止"或"无需停止"。
- **`restart` 继承同一判定**: `ricow restart <name>` 对不存在的名字**在第一步就失败**, 不再先输出假成功文案。
- **文案去矛盾**: 名字存在但确实没在跑的实例, 回执头衔不再说"已停止"; 只陈述"未在运行 (无需停止)"这一件事, 退出码 0。
- **CLI 与 AI 口径统一**: 终端 `ricow stop` 与对话/AI 侧停机工具对同一名字给出**同一条判定结论**(存在 / 不存在), 不存在两套说法。
- **退出码语义明确**: 名字不存在 → 非零; 名字存在但未运行 → 0; 成功停机 → 0; 停机超时未观测到退出 → 保持现状(如实报告)。

**不做**:

- **不改停机执行语义**: 停机指令下发、`--close-all` 平仓、等待退出与超时口径、清理提示(`cleanup_hint_for` 的模式感知文案)一行不动。
- **不改 `server.rs` 停机内核的超时/强杀/台账写入行为**: 本变更只处理"名字判定"与"回执文案", 不动策略子进程的停止过程。
- **不改 `ricow fills X` 的空结果行为**: `无成交记录 (strategy_id=X)` + exit=0 是读查询的正当语义(空集不是错误), 不纳入本次。
- **不改 `start` / `deploy` / `approve` 的名字判定与确认门禁**: 它们已各自正确(含 019 的交互终端逐字短语门禁), 一行不动。
- **不引入新的名字字符集/长度校验**: 沿用现有 `validate_new_name`(用于"生成"路径)与既有安全名字判定, 本次不新增规则。
- **不新增 CLI 子命令或参数**: 不加 `--force` / `--yes` 之类的绕过开关; 判定无条件生效。
- **不做批量停机**: `ricow stop --all` 之类不在本次范围。
- **不改 `status` / `info` / `logs` / `list` 现有输出**: 它们的口径是本次要对齐的基准, 逐字保留。

## 三、用户场景与测试 *(必填)*

### 用户故事 1 - 打错名字时立刻知道"这个策略不存在" (优先级: P1)

用户(或脚本 / AI 工具)想停掉某个策略, 但名字打错了。系统必须让他**当场**知道是名字问题, 而不是给他一张"已停止"的回执。

**优先级理由**: 这是假阴性回执, 直接决定用户是否误判风险已解除。是本次唯一的安全性问题。

**独立测试**: 在任意有 `strategies/` 与 `run/` 目录的环境下, 对一个从未存在过的名字执行停机命令, 检查退出码与输出。可完整独立测试, 交付"打错名字不再静默通过"这一价值。

**验收场景**:

1. **给定** 一个不存在任何策略文件、也不存在任何台账记录的名字, **当** 执行 `ricow stop <该名字>`, **则** 退出码非 0, 输出明确指出"没有这个名字的策略/实例", 且**不含**"已停止"字样。
2. **给定** 同上场景, **当** 执行 `ricow stop <该名字> --close-all`, **则** 行为与场景 1 一致(`--close-all` 不改变名字判定; 也不得因该标志而假装成功)。
3. **给定** 同上场景, **当** 执行 `ricow restart <该名字>`, **则** 退出码非 0, 且输出中**不出现**任何"策略 X 已停止"式的成功回执。
4. **给定** 一个名字, 系统返回"不存在"报错, **当** 用户用 `ricow list` 对照, **则** 报错文案给出的指引足以让他找到正确的名字。

---

### 用户故事 2 - 已经停着的策略, 回执不再自相矛盾 (优先级: P2)

用户对**确实存在、且确实已经停着**的策略再停一次。他期望被如实告知"它没在跑, 这次没有动作发生", 而不是先被告知"已停止"。

**优先级理由**: 这是用户此前质疑的原话残留的一半 —— 回执内部矛盾会直接摧毁用户对停机通道的信任。

**独立测试**: 启动一个策略 → 停掉 → 再停一次, 检查第二次回执的措辞与退出码。

**验收场景**:

1. **给定** 一个已部署且曾运行过的策略, **当** 它已经处于停止状态时再次执行 `ricow stop <name>`, **则** 退出码 0, 回执**只**陈述"未在运行 (无需停止)"一类的单一事实, **不含**"已停止"字样。
2. **给定** 同上场景, **当** 回执读完后, **则** 用户能确定"本次没有动作被消耗、没有清理被触发", 不产生"刚刚停机了一次"的误解。

---

### 用户故事 3 - 终端与 AI 对同一个名字给同一句结论 (优先级: P3)

用户先在终端打错名字拿到报错, 再到对话里问 AI 同一个名字。两边必须说同一件事, 不能一边"不存在"、一边"已停止"。

**优先级理由**: 双口径会让用户无法判断该信哪一边; 也会让 AI 基于错误结论继续行动。

**独立测试**: 对同一组名字(存在的 / 不存在的 / 存在但未运行的 / 运行中的), 分别走终端命令与 AI 停机工具, 逐条比对结论与措辞口径。

**验收场景**:

1. **给定** 一个不存在的名字, **当** 分别走终端停机命令与 AI 停机工具, **则** 两边都判定为"不存在"并拒绝, 且都指向"查看现有实例"的下一步。
2. **给定** 一个存在但未运行的名字, **当** 分别走两条路径, **则** 两边给出同一结论(未在运行 / 无需停止), 不出现一边报错一边成功。

---

### 边界情况

- **daemon 未运行**: 必须优先如实报告"daemon 未运行" —— 此时台账的"未在运行"不具权威性, 不能据此宣称"策略已经停着"(否则用户会以为停机已完成、且不知道确认动作有没有被消耗)。此行为已存在, 本次**必须保持**且不得被新的名字判定绕过。
- **`strategies/<name>.toml` 存在但从未启动过**(无台账记录): 名字"半存在"。按 R1 拍板 —— 判定为**存在**、归入"未在运行 (无需停止)"分支, 退出码 0(与 `ricow status <name>` 在此情形下能成功的事实保持一致)。
- **名字存在、正在运行**: 保持现有成功停机行为与全部文案(含模式感知的清理提示, 如"实盘停机(真实资金)" / "测试网停机(模拟盘, 与真实资金无关)")。
- **名字存在、停机超时未观测到退出**: 保持现状如实报告"未观测到退出" + 非零语义(不静默强杀), 本次不改。
- **大小写 / 前后空白 / 特殊字符的名字**: 沿用既有名字安全判定, 不因本变更放宽或收紧。
- **名字为空串或纯空白**: 必须报错(不得落到"未在运行"分支)。
- **同时存在同名策略文件与同名实例台账**: 视为"存在", 不报错。
- **`restart` 的第一步失败后**: 不得启动任何东西(不得退化成"只启动不停止")。

## 四、功能需求 *(必填)*

### 名字存在性判定(F0)

- **FR-001**: 停机动作必须**先判定名字是否存在**, 再决定是否下发停机指令。判定必须覆盖"策略文件"与"实例台账"两个来源(与 `ricow status` / `ricow info` 同口径)。
- **FR-002**: 名字**完全不存在**(既无策略文件, 也无实例台账)时, 停机动作必须以**非零退出码**失败, 并在输出中明确说明"没有这个名字的策略/实例"。
- **FR-003**: 名字不存在时的输出**不得**包含"已停止"、"未在运行"、"无需停止"任一字样 —— 这些字样只用于名字存在的分支。
- **FR-004**: 名字不存在时的报错必须给出可执行的下一步(指向查看现有实例的命令)。
- **FR-005**: `--close-all` 标志**不得**改变名字判定结果(不存在的名字带不带该标志都失败)。
- **FR-006**: 名字存在但**未在运行**时, 退出码为 0, 输出只陈述"未在运行 (无需停止)"一类的单一事实, **不得**出现"已停止"字样, 且必须让用户明确知道本次没有动作被消耗。
- **FR-007**: 名字存在且**正在运行**时, 行为与现有实现一致(成功停机 + 现有全部附加说明, 含模式感知清理提示)。
- **FR-008**: 名字为**空串或纯空白**时必须报错, 不得进入"未在运行"分支。
- **FR-009**: **`daemon` 未运行时**, 停机动作必须先如实报告 daemon 未运行并失败; 该情形**优先于**名字判定(不得拿台账的"未在运行"宣称策略已停着)。

### 重启继承(F1)

- **FR-010**: `restart` 必须复用与 `stop` 相同的名字存在性判定; 名字不存在时, 必须在**输出任何回执之前**失败 —— 不得先打印停机成功文案再报错。
- **FR-011**: `restart` 在第一步失败后**不得启动任何策略**(不得退化为"只启动不停止")。
- **FR-012**: `restart` 对名字存在的策略, 保持现有"按原实例模式重启、不静默降级"的行为与文案。

### 口径统一(F2)

- **FR-013**: 终端停机命令与 AI 侧停机工具对同一名字必须给出**同一结论**(存在 / 不存在), 不得一边报错一边成功。
- **FR-014**: 名字不存在时的措辞口径与 `ricow status` / `ricow info` 的既有报错保持可辨认的一致(同一类"未找到 / 没有名为"表述), 不新造第三套说法。
- **FR-015**: 判定逻辑必须**单点**(一个判定来源), 不得在 stop 与 restart 各写一份平行实现。

### 不受影响(F3)

- **FR-016**: 本次变更**不得**改变任何停机执行语义: 停机指令内容、`--close-all` 平仓行为、等待退出与超时口径、退出码在真实停机路径上的含义、策略子进程的清理过程 —— 全部保持现状。
- **FR-017**: 本次变更**不得**改变 `status` / `info` / `logs` / `list` / `fills` 的现有输出与退出码。
- **FR-018**: 本次变更**不得**引入绕过判定的开关(如 `--force`), 判定无条件生效。

## 五、关键实体 *(涉及数据时填写)*

- **策略定义**: `strategies/<name>.toml` —— 一个名字是否"已被部署"的依据之一。
- **实例台账**: `run/<name>.json` —— 一个名字是否"曾经运行过"的依据之一, 记录 pid / 模式 / 起止时间 / 上次退出原因。
- **实例视图**: 由"实例台账 + 运行中实例"合成的一份当前快照, 是 CLI 与 AI 判定的共同数据源。
- **停机回执**: 停机动作返回给用户/AI 的文本, 含"是否已退出 / 退出码 / 耗时 / 附加说明"。本变更的靶心就是让这份回执与事实一致。

## 六、成功标准 *(必填)*

### 可度量结果

- **SC-001**: 对**不存在**的名字执行停机, 退出码非 0 的比例 = 100%(现状 0%)。
- **SC-002**: 对**不存在**的名字执行停机, 回执中出现"已停止"字样的比例 = 0%(现状 100%)。
- **SC-003**: 对**存在但未运行**的名字执行停机, 回执中出现"已停止"字样的比例 = 0%(现状 100%), 且退出码仍为 0。
- **SC-004**: 对**同一名字**, 终端与 AI 两条通道给出冲突结论的用例数 = 0。
- **SC-005**: 真实停机路径(运行中 → 停止)的全部既有文案与退出码**零变化**: 逐条比对通过率 100%。
- **SC-006**: 打错名字的用户在一次尝试内即可识别出这是名字错误并找到正确名字(人工判定: 回执包含"不存在"结论 + 可用 `list` 对照的指引)。

## 七、假设

- 假设"停机"是一个**风险动作**, 因此在"名字不明确"时一律选择**报错**而非"静默无事发生" —— 宁可让用户多敲一次命令, 不可给出可能被误读为风险已解除的回执。
- 假设 `ricow status` / `ricow info` 现有的"未找到策略或实例"报错已被用户接受为正确口径, 本次以其为对齐基准, 不另立标准。
- 假设 AI 侧停机工具现有的严格判定不需要放宽(它已经比 CLI 严格), 对齐方向是**CLI 收紧**, 而不是 AI 放宽。
- 假设本次不涉及多语言文案改造(CLI 侧输出为中文, AI 侧沿用其现有中英双语机制), 不新增翻译面。
- 依赖: 实例视图的既有合成逻辑(台账 + 运行中实例)可被停机路径复用, 无需新增数据源。
- 依赖: daemon 未运行时的"先报 daemon 未运行"行为已存在, 本次只要求不被破坏。

## 八、已定稿决策 *(原待澄清项, 2026-09-20 拍板)*

- **D1(原待澄清 1) — `strategies/<name>.toml` 存在但从未启动过时的处置**: 判定为**存在**, 归入"未在运行 (无需停止)"分支, **退出码 0**。
  - **理由**: 与 `ricow status <name>` 在此情形下能成功返回实例视图的事实保持一致; 名字是否"已被部署"由策略文件决定, 名字是否"曾经跑过"由台账决定, **两者取并集**才是"名字存在"的完整口径(即 FR-001)。
  - **影响**: FR-001 的两个来源为**并集**, 缺一不算不存在; FR-002 的"完全不存在"= 策略文件与台账**皆无**。
- **D2(原待澄清 2) — AI 侧与 CLI 的判定关系**: **合并为单一判定来源**, 取消 AI 侧现有的、只认实例台账的更严格判定。
  - **理由**: 双口径会让用户无法判断该信哪一边(用户故事 3 的核心痛点); 合并后 CLI 与 AI 对同一名字必然同结论, 从结构上消除"一边报错一边成功"的可能。
  - **影响**: FR-013 的"同一结论"由**同一份判定实现**保证, 而非两处各自实现后人工比对; FR-015 的"单点判定"是 D2 的直接落地要求。
  - **保留**: AI 侧"daemon 未运行必须先报 daemon 未运行"(见边界情况)这一**优先级**不变 —— 合并的是名字判定, 不是 daemon 状态判定。
