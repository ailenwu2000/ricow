## 三、计划外发现(均由真实链路暴露)

1. **重复投递**: 批量替换 `on_fill` 行时, 16 空格缩进的匹配串命中了 24 空格缩进的 live 主循环那行(子串匹配),
   同一成交发两次通知。**实测数据暴露**: db 记录 2 笔 vs 收到 3 条成交通知 → 定位并删除重复块, 复验 1 笔=1 条。
   > 教训: 批量文本替换必须带**唯一性锚点**(整行含缩进 + 邻行), 不能靠"看似足够的缩进"。
2. **数值尾差进入给人看的文本**: 通知出现 `0.0040000000000000000832667269`(Lua f64 → Decimal)。
   新增 `fmt_num`(round_dp(8) + normalize)统一规整; **下单路径不受影响**(引擎本就按 step/tick 对齐),
   诊断日志仍保留原值以便追因。
3. **Dry Run 清理回调的成交漏通知**: dry_run 停机清理后的成交循环缩进与主循环不同, 首轮批量替换未覆盖 → 补齐。

## 四、收敛遗留

1. **未接真实第三方通道**: 用本地回环端点验证真实 HTTP 往返(SC-003); 具体 Telegram/飞书 token 由用户自备, 未在本变更验证。
2. 通知不保证送达(不重试、不排队, A2)—— 有意为之, 不视为缺口。
3. 通知内容为纯文本(不带按钮/附件); 若日后需要交互式确认(如"一键停机"), 属新变更。

## 五、留档教训

1. **产品承诺项要能被"看见"**: 熔断/强平/残留这类事件原本只写日志 —— 用户不在终端前就等于没有。通知的价值不在技术复杂度,而在**把已有信号送到人眼前**。
2. **投递必须单向且无背压**: spawn + 超时 + 不重试, 是本模块唯一可接受的失败模式(实测端点不可达时循环零影响)。
3. **`params` 通道也能承载运维配置**: `notify_*` 前缀足够表明用途, 避免为 5 个字段改动 20+ 处结构构造点(与 014 的 `liq_warn_pct` 同一口径)。
