用户于 2026-10-14 明确选择:

| #      | 问题                      | 决策                         | 理由                                                                                                                       |
| ------ | ----------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **D1** | 约束是硬断言还是指导性建议           | **指导性建议**                  | 静态代码分析判断不出真实回撤(要跑回测才知道); 且平台立场是不做风控。回撤由 **P4 样本外回测**去暴露, 不在生成时拦截。                                                        |

### D1 的直接后果(必须写进实现约束)

**档位映射出的所有数字, 都是"提示词里的目标", 不是"生成后的拦截条件"。**

- 后端**只校验输入合法性**(范围、类型、互斥), **不校验产物是否满足目标**;
- 唯一的例外是 D2 的**止损线索警告**(P5 的 `lint_lua` 第 6 类)—— 且它**只警告不拦截**;
- 「实测回撤超目标」这件事只能在 P4 的回测里**显示给用户看**, 不阻断流程。

**为什么不让它硬性拦截**(写下来免得后人当缺陷修): 实测超限 ≠ 策略违规 —— 可能是回测窗口恰好特殊。  
把它做成 409 会让"用户换了窗口跑一次"和"策略真有缺陷"无法区分, 与 053 那条"不拿失真的比率指标下结论"  
是同一类判断。

### 自定义档的行为定义(D3 的直接后果)

**它不是"第四列固定数值"**, 而是:

1. 选中后**展开全部数值字段**(`max_drawdown_pct` / `max_position_pct` / `leverage_cap` /  
   `min_spacing_pct`), 全部**必填**;
2. 不提供默认值 —— 给了默认值就等于偷偷帮用户选了档;
3. 提示词按**用户填的实际数字**生成约束文字(与三档走同一条渲染路径, 只是数值来源不同);
4. 前端文案不给"这档意味着什么"的解读 —— 那是用户自己的决定, 界面**只显示他填了什么**。

## 三、D2 落地: 按策略类型给出不同的"保护要求"

提示词里**不能只写"必须有止损"**。按类型分支:

| 策略类型              | 等价保护要求(写进提示词)                                                                                                                                       |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **趋势 / 突破 / 择时类** | 必须有**明确止损**: 价格或回撤触线即平仓; 禁止无止损的逆势加仓                                                                                                                 |
| **网格 / 再平衡类**     | 等价保护三件套: ① **仓位上限**(单笔 ≤ 档位值); ② **最小间距下限**(见映射表, 防磨损); ③ **爆仓/深亏监控**(合约须有 `liq_*` 类告警, 参照内置 `liq_warn_ratio = 0.1`)。**不强行要求止损** —— 网格的自我保护机制是再平衡本身 |

**类型判定由谁做**: 由 **AI 自己按用户 `idea` 判断**并在产物里体现, 后端**不猜测类型**。  
理由: 用户可能描述一个混合形态, 后端硬分类会误判; 而"类型"本来就该由理解意图的一方决定。

**唯一的机械兜底**: `lint_lua`(P5 第 6 类)在**两类保护线索都找不到**时给 warning ——  
即"既没有止损关键词、也没有仓位上限/爆仓监控线索"。这仍是**警告不拦截**(D1)。

## 四、必须遵守的实现约束(供 plan/tasks 直接引用)

1. **单点定义**: 映射表只在后端一处定义; 前端"档位含义"文案与提示词**都从它派生**。  
   加一条单测锁住"三处一致"(或断言前端文案由后端返回 —— 更稳)。
2. **结构性互斥校验**:
   - `market = spot` 且给了 `leverage_cap` → **400**(现货无杠杆, 不接受无效输入);
   - 自定义档缺任一必填字段 → 400;
   - 数值范围: `initial_cash > 0`、`max_drawdown_pct ∈ (0,100]`、`max_position_pct ∈ (0,100]`、  
     `leverage_cap ∈ [1, 10]`(与 `max_leverage` 上限一致)、`min_spacing_pct > 0`。
3. **提示词覆盖断言**: 每个非空字段**必须**出现在 `build_generate_prompt` 输出里 —— 加单测逐字段断言。  
   否则字段就是装饰(违反 `plan.md` 原则 3)。
4. **目标是目标, 不是断言**: 提示词措辞用"目标是…"而非"必须…" 除非该项**可静态验证**  
   (只有"杠杆上限"可静态验证 → 它写入 TOML 由 `validate_leverage` 真正执行)。  
   **055 B1 修正**: 写入的是 `[backtest].max_leverage`(**上限**), 不是 `[backtest].leverage`(**实际**)。  
   后者会被 `commands/run.rs` 在启动实盘/demo 时读走并真的设到交易所 —— 那等于平台替用户开杠杆,  
   而且是在他以为自己选了"更稳"的时候。**上限与"就用多少"是两件事, 后者只能由用户自己决定。**  
   **055 B2 修正**: 同一个上限也必须进**验证回测**(`verify_spec.max_leverage`), 否则合约策略
   "生成时看到的成绩"与"保存后看到的成绩"是两个口径, P1 的生成即验证在合约场景等于白跑。
5. **`initial_cash` 是唯一真下场的数字**: 它写进策略 TOML `[backtest]`, 让回测口径与用户真实资金一致。  
   其余都是**生成时的约束语义**。

## 五、第 2 项已定: P1 自动回测窗口(2026-10-14)

### 决策

**默认 90 天, 但用户可选 90 / 180 / 360, 或手动输入任意天数(1–3650)。周期 = 生成时用户选定的 interval。**

用户选择的理由(优于审定者原提议的"写死 90"): 写死窗口会让想看样本外的人无路可走;  
给选项则把"窗口多久"这个真实决策交回用户 —— 同时解决了本文件 §五 第 3 项(P4 样本外切分)  
在 90 天窗口下"样本外只剩 27 天"的困境: 想看样本外的人自己拉长即可。

### 为什么 90 是对的默认值(不是新定的数 —— 是确认既有收敛)

核对结果: **90 天已经是全项目四个回测入口的统一默认**:

| 入口                                       | 位置                                  | 默认                 |
| ---------------------------------------- | ----------------------------------- | ------------------ |
| AI 工具 `run_backtest`                     | `ai/tools.rs:400`                   | "默认 90"            |
| AI 工具 `preview_strategy`(生成即回测)          | `ai/tools.rs:854`                   | "默认 90"            |
| Web 回测接口 ×3(backtest / sweep / optimize) | `web/backtest_jobs.rs:535,762,1063` | `unwrap_or(90)`    |
| 前端回测卡天数字段                                | `assets/strategies.js:853`          | `value="90"`       |
| 影响评估窗口(053 写死)                           | `assets/strategy_backtest.js:1010`  | `ASSESS_DAYS = 90` |

生成后自动回测**若用别的数字, 就会让生成的结果与用户自己点回测得到的数字不可比** ——  
这比"选哪个数字"重要得多。

### 周期: 复用生成时选定的 interval, **不固定 1h**

- 用户在生成弹窗选了 `1h`, 就该看到 1h 的 90 天回测 —— 直观且可解释。
- **不按周期缩放窗口**(不要"折算成等强度"): 用户选了 4h, 就是要看 4h 下的 90 天。
- 与影响评估的差异(评估固定 `1h`)是有意的: 评估是**两次跑对比**, 唯一变量必须是参数,  
  所以要固定; 生成后的首次验证是**单次展示**, 应贴合用户意图。

### 边界与如实告知(不放任静默变慢)

- **360 天在 1m 周期下 = 518,400 根**(上限 `MAX_BACKTEST_BARS = 13_000_000`, 仅占 4.0%)——  
  任何周期 × 任何可选天数都**不会撞 bar 预算**, 无需额外拦截。
- 但天数越大**拉数与回测越慢**。用户选 360 天时必须**如实提示预计更慢**, 不静默变慢  
  (与实时行情"三态 chip + 最后更新时刻, 绝不静默降级"同一纪律)。
- 手填天数沿用既有范围校验 `1..=3650`(`backtest_jobs.rs:506-508` 已有该 400)。

### 与 P4 的衔接

P4 的样本外切分(70/30)在 90 天下每段仅约 63/27 天。**不把默认窗口调大去迁就 P4** ——  
而是: ① 样本外过短时**如实报"样本不足"而不硬切**(与本文件 §一 D1 同类的诚实纪律);  
② 在 P4 的过拟合警示文案里**引导用户拉长窗口重跑**。这是本项目一贯做法  
("拿不准就说拿不准", 见 `AI_ASSESS_PREAMBLE`)。

## 六、第 3 项已定: P4 样本内外切分(2026-10-14)

### 关键前提: **零引擎改动**

核对结果: 引擎**早已原生支持显式起止窗口**, P4 只是编排。

| 能力                                       | 位置                             | 状态              |
| ---------------------------------------- | ------------------------------ | --------------- |
| CLI `--start` / `--end`(YYYY-MM-DD, UTC) | `commands/backtest.rs:37-43`   | ✅ 已支持           |
| Web `BacktestRequest.start` / `.end`     | `web/backtest_jobs.rs:366-371` | ✅ 已透出(**前端未用**) |
| 起止 → days 换算                             | `commands/backtest.rs:875-882` | ✅ 已实现           |

→ **P4 = 算两个日期区间 → 跑两次回测 → 并排展示**。不要新写引擎能力。

### 决策(用户 2026-10-14 选择)

| #      | 项      | 决策                                                 |
| ------ | ------ | -------------------------------------------------- |
| **D4** | 切分方式   | **前半段 / 后半段**(时间顺序): 样本内 = 窗口前 70%, 样本外 = 后 30%    |
| **D5** | 最短样外门槛 | **默认 30 天, 可选 90 / 180, 或手填**; 门槛拉高时**如实提示可能耗时更久** |
| **D6** | 退化提醒   | **仅打标不判定** —— 不给"过拟合"定性                            |

### D4 的理由(必须写下来, 免得后人"优化"成随机切分)

**"70/30 切分"在时间序列上有两种含义, 只有一个是对的:**

- ✅ **前半段 / 后半段**(前 70% 时间 → 后 30% 时间): 用**过去**验证**未来**, 与 `specs/backtest.md §一`  
  的无前视铁律一致。
- ❌ **随机 / 交错 70/30**: 随机抽 K 线做样本内 —— **在时间序列上是错的**, 抽样会把未来信息漏进  
  训练集, 等于**自己制造前视偏差**。这直接违反项目最高约束。

**禁止实现随机切分。** 若将来有人提"随机切分更均匀", 答案是这个。

### D5 的两级门槛(分层, 不是单一硬线)

| 样本外天数            | 呈现                                           |
| ---------------- | -------------------------------------------- |
| < 30 天(或 < 手填门槛) | **如实说"样本不足, 不给结论"** + 引导拉长窗口重跑。**不硬切、不硬给数字** |
| ≥ 30 天(默认门槛)     | 给出样本外指标, 标注"已达最低可信线"                         |
| ≥ 90 天           | 标注"样本充足", 结论更可托付                             |

**与第 2 项的一致性收益**(值得说明): 窗口选项 90/180/360 天 × 30% → 样本外 27/54/108 天。  
即默认 90 天窗口**刚好卡在 30 天门槛之下**(27 天) → 系统会提示"建议拉长到 180 天再看样本外",  
而用户拉长即得 54 天。**两个决策联动, 形成一条自然引导路径**, 不需要去调大默认窗口。

D5 的"可选 90/180"不是多余: 它们是**更高标准的自选线**, 与"默认 30"是门槛与更高要求的关系,  
不是三个并列的门槛。

### D6 的措辞约束(只打标, 不判定)

触发打标(任一满足):

- 样本外**净盈亏 < 0**; 或
- 样本外**最大回撤 > 样本内最大回撤 × 1.5**。

**标记文案必须说"样本外退化", 不得说"过拟合"**。理由: 样本外表现差有多种成因  
(行情状态变了 / 策略本身就弱 / 窗口太短), 一概归因为过拟合会**超出证据能支撑的范围** ——  
与本文件 §一 D1 是同一类判断, 也与 053"不拿失真的比率指标下结论"同一纪律。

打标文案必须**同时给出**"建议拉长窗口重跑"的引导(D5 <  30 天时的处理一致)。

### 与 P4-3(walk-forward)的边界

D4 是**单次前后切分**(两段, 70/30), 回答"参数是不是过拟合"。  
walk-forward(§八)是**另一个东西** —— 它是**多段滚动**, 回答"策略在不同行情阶段稳不稳"。

**两者并存, 不是替代关系**, 且**切分逻辑不同**(见 §八 D9 的形态区分)。  
实现时**不要把 D4 的两段逻辑顺手扩成多段**, 那是把两个语义混成一个。

## 七、第 4 项已定: `origin` 标记的落盘位置(2026-10-14)

### 决策(用户 2026-10-14 选择)

| #      | 项    | 决策                                                             |
| ------ | ---- | -------------------------------------------------------------- |
| **D7** | 落盘位置 | **注释标记**: 在策略 TOML 写一行 `# ricow:origin = ai`。**不新增 schema 字段** |
| **D8** | 徽章语义 | **只说来源, 不说验证** —— 徽章 = "AI 生成", **不含"已验证/未验证"**                |

### D7 的依据: 与既有诚实性标记同一哲学

项目现有的两个诚实性标记**都是"从磁盘事实推导", 不是"存下来的字段"**:

| 标记                             | 来源                       | 位置                   |
| ------------------------------ | ------------------------ | -------------------- |
| `declared: bool`               | 磁盘上**有没有**同名清单 TOML      | `catalog.rs:340-393` |
| `duplicate_of: Option<String>` | 脚本是否与某内置**逐字相同**(归一化换行后) | `catalog.rs:141-145` |

`origin` 属于同一类信息 → **跟随同一做法**, 不破例新增 schema 字段。

**为什么不用正式字段**(写下来免得后人换回去):

|       | 正式字段 `origin = "ai"`     | 注释标记 `# ricow:origin = ai` |
| ----- | ------------------------ | -------------------------- |
| 性质    | 用户**可改的声明**              | 磁盘上的**事实**痕迹               |
| 准确性   | 用户手改 / AI 改写后**就不准了**    | 只在用户主动删注释时才丢               |
| 默认值   | 需处理"缺失"与"未知"             | **找不到注释 = 用户策略**(安全默认)     |
| 与既有做法 | 不一致(declared 明明可推导, 也没存) | 一致                         |

**注意两个 TOML 的区别**: 策略有**清单 TOML**(`strategies/{market}/{id}.toml`, 表现层)与  
**实例 TOML**(`strategies/{id}.toml`, 运行配置)两份。注释写在**实例 TOML** ——  
`POST /api/strategies` 落盘时写(`strategy_io/mod.rs:1365` `save_strategy`)。

### 可被删除是**特性不是缺陷**

用户删掉注释 = 明确表示"我知道这份是 AI 写的, 不需要提醒我" ——  
与项目既有的 `CatalogEntry::blocks_run`（`catalog.rs:148-155`「用户明确写过清单就**只标记不拦**,  
拦截权还给他」）**同一立场**。实现时不要为"防篡改"而改成正式字段或校验和 —— 那会把  
"提醒"变成"管控", 超出这条信息该有的分量。

**安全默认**: 解析不到注释 → 当作普通用户策略(不显示 AI 徽章)。绝不反过来默认成 AI。

### D8 的依据: 防止徽章被 P1 架掉(重要)

**P1 定了"生成即回测"** → 所有 AI 策略**一生成就带回测结果**。  
若徽章含"已验证/未验证", 则"未验证"几乎**永远不会出现** → 徽章退化成冗余 UI。

**故: 徽章只表达来源("AI 生成"), 验证状态交给 P1 的回测结果自己展示** ——  
两者各说各的事, 不互相抢活。

这也**修正了 `audit.md` 问题 #3 的一半**: 审计原文建议徽章分「AI 生成 · 未验证」→  
「AI 生成 · 已验证」两态。**该建议在 P1 落地后不再成立**, 以本决策为准。

### 成本前提(核对出的两个硬约束, 决定了整个方案形态)

| 约束                                      | 位置                       | 含义             |
| --------------------------------------- | ------------------------ | -------------- |
| `MAX_COMBOS = 100`, 每组 = 一次全窗口回测        | `optimize.rs:18`         | 一轮寻优 = 100 次回测 |
| **寻优是串行**(`for combo in combos.iter()`) | `optimize.rs:218`        | 无并行, 时间线性累加    |
| 同一策略同时只允许一个 running 作业(409 busy)        | `backtest_jobs.rs:37,88` | Web 层无法叠加并发    |

→ **两种形态的成本差约 100 倍**:

| 形态           | 回测次数                 | 量级           |
| ------------ | -------------------- | ------------ |
| 固定参数、挪窗口(默认) | **N 次**(N = 段数, 2–5) | 与单次回测同级      |
| 每轮重寻优(可选)    | **N × 100 次, 串行**    | 分钟级 → 可能十分钟级 |

**这是"重寻优必须做成可选开关"的唯一理由** —— 不是功能次要, 是成本高两个数量级。

### D9: 两种形态是**不同的切分逻辑**, 不要混实现

|          | 形态 A: 固定参数(默认)       | 形态 B: 每轮重寻优(可选)                             |
| -------- | -------------------- | ------------------------------------------- |
| 参数       | **全程不变**             | 每轮用**验证段之前**的数据重新寻优                         |
| 切分       | 窗口**均分** N 段, 每段独立回测 | 第 i 轮: `[起点, T_i]` 寻优 → `(T_i, T_{i+1}]` 验证 |
| 是否需"训练段" | **不需要**(参数不是从数据学的)   | **必须**, 且不得越界                               |
| 拼起来      | = 覆盖整个窗口的分段表现        | = 一条**仅覆盖验证段**的样本外曲线                        |
| 回答的问题    | 策略在**不同行情阶段**都行吗     | 我的**调参过程**是不是在过拟合                           |
| 依赖       | 无, 可独立交付             | **依赖 P4-2**(`optimize` 接通)                  |

**术语纪律**: 形态 A 严格说是"滚动窗口分析(rolling window analysis)",  
经典 walk-forward 指形态 B。UI 文案**不要统称 walk-forward 让用户以为两者等价** ——  
形态 A 说「分段验证」, 形态 B 说「滚动验证(含重新调参)」。

### D10: 段数自动规则(可单测, 必须显式)

```
段数 = clamp(floor(总天数 / 60), 2, 5)
校验: 每段天数 = 总天数 / 段数, 必须 ≥ 30; 否则报"窗口过短"并建议拉长
```

| 窗口       | floor(/60) | 段数        | 每段   | 判定                         |
| -------- | ---------- | --------- | ---- | -------------------------- |
| 30 天     | 0          | 2         | 15 天 | ❌ < 30 → **报"样本不足"**, 不给结论 |
| 60 天     | 1          | 2         | 30 天 | ✅ 刚好卡线                     |
| 90 天(默认) | 1          | 2         | 45 天 | ✅                          |
| 180 天    | 3          | 3         | 60 天 | ✅                          |
| 360 天    | 6          | **5**(上限) | 72 天 | ✅                          |

**30 天门槛沿用 D5** —— 同一个"最短可信样本"口径, 不另设一份。

**形态 B 的段数要更保守**: 成本高两个数量级 → **上限压到 3 段**, 且不随窗口自动增长。  
理由: 形态 B 的价值在"验证调参过程", 3 段已能看出参数是否稳定; 更多段只增加成本不增加信息。

### 呈现与如实告知

- **形态 A**: 每段一组指标, 并排 + 离散度提示(如"第 2 段明显跑输, 该策略可能只适合特定行情")。  
  沿用 D6 纪律: **只描述差异, 不下"过拟合"定论**。
- **形态 B**: 拼出样本外曲线, 与形态 A 的"全窗口曲线"并列展示(两条线含义不同, 需图例说明)。

  与本文件"天数越大越慢如实提示"、"绝不静默降级"同一纪律。
- **走异步作业 + 进度**(复用 `backtest_jobs` 的作业队列与 409 busy), 不可同步阻塞。
- 失败/超时**如实报**, 保留重试入口。

### 实现顺序建议
