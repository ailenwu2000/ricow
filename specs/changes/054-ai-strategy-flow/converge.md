### 2.1 为什么档位要落成数字，而不是把「保守」这个词传给模型

「保守」对模型不是约束，是**风格建议**。同一个 prompt 里写"用户想要保守一点"，
模型给出的是它自己理解的保守 —— 而用户以为自己选了档。落成数字后，
提示词里出现的是「单笔仓位 ≤ 10% / 网格间距 ≥ 0.8%」，**可验证、可复现、可对照**。
数字来源也写在 `risk_profile.rs` 顶部注释里：全部取自内置策略实测值或引擎硬上限，不是拍脑袋。

### 2.2 为什么 `origin` 用注释而不是正式字段

`# ricow:origin = ai` 与 `declared` / `duplicate_of` 同一哲学：**能推导的就不存**。
存一份"这是 AI 写的"会和代码本身分叉（用户把代码改光了它还是 ai）。

### 4.1 一句话、一笔钱，只换档位 —— 两份产物的对照（P2 的真跑证据）

同一句 `我想稳一点, 做一个低风险的网格, 别大起大落`、同一笔 `initial_cash=10000`、
同一标的 `ETHUSDT 1h`、同样验证 30 天，**唯一差别是 `risk_tolerance`**：

| | 保守档 conservative | 激进档 aggressive | 档位表（对照） |
|:--|:--|:--|:--|
| 网格间距下限 | `min_spacing_pct = 0.008`，说明里写「低于 0.8% 时被强制提升到 **0.8%**」 | `min_gap_pct = 0.0045`，说明里写「代码硬性不低于 **0.4%**」 | 保守 **0.8%** / 激进 **0.4%** |
| 单笔（单档）仓位 | `order_pct = 0.08`（**8%**） | `max_position_pct = 0.45`（**45%**） | 保守 ≤ **10%** / 激进 ≤ **50%** |
| 回撤目标 | `max_drawdown_pct = 0.10`（**10%**） | `max_drawdown_pct = 0.35`（**35%**） | 保守 ≤ **10%** / 激进 ≤ **40%** |
| 加仓层数 | `max_lots = 4` | `max_layers = 8`（另有 `max_total_quote = 4000`） | 保守**禁止**单边加仓 / 激进允许但须有上限 |
| 代码长度 | 13216 字符 | 11566 字符 | —— |

两份代码**不逐字相同**，且 `max_position_pct` 只在激进档那一份里出现（保守档 0 次 / 激进档 5 次）。
**结论：档位不只进了提示词，真的落进了代码** —— 这正是 P2 唯一有效的证据
（离线单测只能证明提示词里有那段话，证明不了模型会照做）。

顺带验到的两件事：

- **P1 生成即验证是真的跑了**：两份 `verify.ok = true`，各 720 根 1h K 线；
  保守档成交 9 笔、净盈亏 −13.61、最大回撤 2.21%、基准 −10.90%。
- **T37 也真的回来了**：
  - 保守 `summary` = 「1h现货网格:ATR间距分档买入,4h趋势过滤,逐档止盈,跌幅及回撤触发清仓」；
    激进 `summary` = 「ATR定间距分批买入, 每格涨一格止盈; 仓位三重封顶, 回撤熔断或浮亏硬止损即清仓」。
    都是**只讲代码里有的东西**（提示词里「只作背景」的那句用户原话没混进来）。
  - `manifest_params` 保守 14 项 / 激进 19 项，中文名 + 说明 + 默认值齐备。
- 还有一条旁证：不带本金直接生成 → **400**
  「缺少 initial_cash：不知道投多少钱，就无法换算『单笔不超过百分之几』」。
  老路径（一句自然语言就生成）**已经不存在了**。

### 4.2 真跑发现并修掉的一处缺陷：验证回测没用用户填的本金

第一版真跑（改之前）的报告里写着「投入资金: **100000** USDT」，而用户填的是 **10000**。
根因：`verify_generated()` 里 `cash: None`，一律按**默认 10 万**跑；
而给模型的提示词说的是「用户准备投入 {initial_cash} USDT」。
这直接冲突于 spec §四-2「让回测口径与用户真实资金一致」——
**仓位是否拒单、手续费占比、网格能不能铺满，在小资金下完全是另一回事**，
用户填 1 万却看到 10 万的成绩单，等于被悄悄换了一个人替他跑。

修法：`cash: Some(initial_cash)`，并把入参组装抽成 `verify_spec()` **纯函数**，
加单测 `test_verify_spec_runs_on_users_own_cash_not_the_default` 钉住
（跑回测本身要联网、测不了，只能靠真跑发现 —— 这正是真跑的独有价值）。

**修复已复跑验证**：上面 §4.1 那两份报告里「投入资金」都是 **10000**（脚本里的断言两处皆 PASS），
不再是 100000。

### 4.3 中途踩到的上游故障（如实记）

对照表不是一次跑出来的：真跑到后半程上游 DeepSeek 开始**挂起** ——
`POST /api/strategies/ai-generate` 两次各 900s / 1500s 超时无响应；
绕开 ricow **直连 `api.deepseek.com/chat/completions`**（16 token 的极简请求）
也是 240s / 60s 拿不到响应体，而 `/models` 端点同时是秒回的
→ 判定为**上游故障**，与代码无关（同一份代码前半程跑成功过）。
**次日用同一份二进制重跑，两次生成各 ~150s 全部成功**（即 §4.1 那张表）。

### 4.4 由此暴露的一个**遗留项**（本轮没动）

AI 客户端**没有超时**：`build_client()` 直接 `openai::Client::builder()`，
reqwest 默认**不设 timeout**，于是上游一挂起，Web 请求就**无限等待**（浏览器一直转圈）。
`is_retryable_llm_error()` 只兜「有错误文本」的瞬时故障，兜不住「连上了但不回」。
修法是给 HTTP 客户端设一个总超时（rig 的 `ClientBuilder::http_client` 允许传自定义
`reqwest::Client`）—— **本轮刻意不做**：超时值需要单独定（生成一份完整策略正常要 ~100s，
定短了会误杀），且要在上游正常时复测才敢定，属于下一轮的事。已在此留痕，别当 bug 悄悄修。

## 六、CDP 抓到的那处真缺陷（`skipBox` TDZ）

`strategies.js` 里 `slowHint.hidden = skipBox.checked` 写在
`const skipBox = document.createElement("input")` **之前** →
AI 生成弹窗**一打开就 `ReferenceError: Cannot access 'skipBox' before initialization`**。

**语法检查 / 中英键一一对应 / 引用完整性扫描 / Rust 单测 / Python 冒烟—— 四道静态门全绿**，
因为它们都读字符串，进不了浏览器运行期。这就是保留 CDP 这一层的全部理由。
已修（把 `skipBox` 提到 `slowHint` 之前）。

### 8.1 B1（最严重）：杠杆「上限」被写成了实际杠杆 —— 平台替用户开 2~5 倍杠杆

完整链路（逐环确认到行号）：

| 环节 | 位置 | 行为 |
|:--|:--|:--|
| 档位定义 | `risk_profile.rs:102/111/120` | 保守 2x / 稳健 3x / 激进 5x，语义是**上限** |
| 前端落盘 | `strategies.js` 保存体 | `leverage: draft.leverage_cap` —— 写成 `leverage`，不是 `max_leverage` |
| 后端写 TOML | `strategy_io/mod.rs` `save_strategy` | `bt.leverage = Some(v)` → `[backtest].leverage` |
| 参数解析 | `ricow_strategy/config.rs:307` | `leverage` = **实际杠杆**（默认 1.0）；`max_leverage` 才是上限（默认 10） |
| 实盘出口 | `commands/run.rs:292-296` | `config.get_f64("leverage").or(backtest.leverage).unwrap_or(1.0)` → `ex.prepare(pair, leverage, …)` **真的设到交易所** |

**后果**：用户只是点了个「保守」形容词，就被设定为 2x 实盘杠杆（激进档 5x）。
手写策略与内置策略默认都是 **1x** —— **AI 生成这条路径是唯一会主动替用户加杠杆的入口**，
而且是在用户以为自己在选"更稳"的时候。UI 上写的是「合约杠杆上限 2x」，落盘后它成了「就用 2x」。

**根因在 spec 自己**：`spec.md §二` 的档位表写的是「写入 TOML `[backtest].leverage`」，
实现忠实照做。已把 spec 与实现一并改成 `max_leverage`。

**为什么测试没抓到**：e2e 只断言了源码里存在 `leverage: draft.leverage_cap` 这个**字符串**，
从没断言落盘语义。已补一条反向断言 + 一条 Rust 单测
`test_save_request_writes_tier_cap_as_max_leverage_not_as_actual_leverage`。

### 8.2 B2：验证回测不带杠杆上限 → 合约「生成即验证」的成绩是假的

`verify_spec` 里 `max_leverage: None`（→ 引擎默认 10x），而保存时档位写的是 2/3/5x。
于是合约策略**生成时给你看的成绩**与**保存后点回测看到的成绩**不是一回事 ——
P1「不用先存盘就能看到它在历史上是什么表现」在合约场景等于白跑。

这与 §4.2 那条「验证回测没用用户填的本金」是**同一个 bug 的另一半**：
本金那半在 T41 真跑时修了，杠杆这半漏了。已一并修，并加单测
`test_verify_spec_carries_the_tier_leverage_cap` 钉住（回测要联网，测不了，只能靠纯函数断言）。

### 9.1 B3：档位目标的**事后核对**

**缺口**：档位此前**只对模型有约束力**。提示词说"回撤目标 ≤10%"，但生成完界面只把实测的 25%
显示成一个红数字，从不说"你选的是 10%，没达到"。用户得自己记住选了什么、再去比对 ——
"我选了保守档"这句话在用户侧没有任何反馈闭环。这是"能否满足普通投资者需求"上最大的缺口。

**实现**（`risk_profile.rs::tier_check` 纯函数 → `VerifyOutcome.tier_check` → 前端 `renderTierCheck`）：
紧贴指标卡下方显示「目标 ≤10% / 实测 25.3% / 未达到目标」。

三条刻意的边界：
- **只核最大回撤一项**。单笔仓位、网格间距、杠杆上限是**代码属性**，回测指标里根本没有
  对应数字 —— 凑一个"核对"出来就是编造实测值，比不核对更糟（单测
  `test_tier_check_only_covers_what_the_backtest_can_measure` 钉住范围）。
- **没有实测值就不下发核对框**（`metrics` 为 None / 自定义档无目标 → `None`），
  不摆一个"目标 10% / 实测 —"的空壳 —— 那是用界面暗示"已经核过了"。
- **措辞是"未达到目标"不是"不合规/失败"**（D1 同源：档位写的是目标不是断言）；
  测不出来就标 `unknown`，不填 0 冒充实测。

**真跑证据**（保守档 / 1 万 U / ETHUSDT 1h / 验证 30 天）：
`tier_check = {"tier_zh":"保守","items":[{"key":"max_drawdown_pct","target":10.0,
"actual":2.975,"verdict":"met"}],"unmet":0}` —— 目标来自档位表、实测来自回测、判定真的做了。

### 9.2 B4：lint 整份级警告不再被逐行噪音挤掉

**缺口**：`lint_lua` 原本一个 8 条总上限同时管逐行类与整份级第 6 类。而逐行类**每行都能触发** ——
十行 `config_f64(...) or ...` 就把配额吃满，于是"这份脚本会下单但没有任何止损线索"
（对普通投资者最要紧的一句）恰好就是看不见的那句。

**改法**：`LINE_WARN_CAP` 只管逐行；整份级**先算先放**，排在第一位，不占逐行配额。
单测 `test_lint_lua_whole_file_warning_survives_a_flood_of_line_warnings` 用 12 行触发行 + 一行下单
验证它仍在、且在第一条。

### 9.3 B5：AI 请求总超时

**缺口**：reqwest 默认**不设超时** —— 上游一挂起，Web 请求永远悬着，用户只看到页面一直转圈，
连"是网络问题还是模型问题"都无从判断（真跑时实测踩到：900s / 1500s 拿不到响应体，
而同一端点的 `/models` 秒回）。

**先试过、走不通的一条**：直接给 rig 传一个自带 `.timeout()` 的 `reqwest::Client`
（`ClientBuilder::http_client`）。编译报 `reqwest::Client: HttpClientExt` 不满足 ——
依赖树里有**两个 reqwest**：本仓 0.12，而 rig 0.42 用的是 **0.13**，类型根本对不上。
为本仓把 reqwest 升到 0.13 会牵动交易所那条线，不值得。

**最终实现**：`tokio::time::timeout` 套在**每一次**调用上（非流式 `ask_once` / 流式 `stream_once` /
连通校验 `probe` 三处）。默认 **300 秒**（一次完整生成实测约 150 秒，取一倍余量），
可在 `ricow.toml` 的 `[ai].timeout_secs` 放宽（10..3600，本机小模型的口子），非法值报错给解法。

**超时不重试**（`is_retryable_llm_error` 里前置否决）：一次就等满 300 秒，退避重试两次是十几分钟，
用户根本等不起，而且上游多半仍无响应。报错文案说清三件事：等了多久、不是本机的错、怎么调大。

### 9.4 B6：两条生成路径的口径对齐

**缺口**：Web 单发生成把本金当必填项、真的用它跑验证回测；而 CLI 对话路径的 `preview_strategy`
**根本没有本金入参** —— 助手即使用户说"我投 1 万"问到了，也没地方传，回测一律按内置默认 10 万跑。

**改法**：`preview_strategy` 新增 `initial_cash`，落到 `params.cash` —— 与 CLI `--param cash=`
**同名同义**，走 `BacktestParams::resolve` 既有的三层合并，**不新增一套口径**。
没传时回包**如实写明**"本次按内置默认本金 100000 USDT 跑 —— 这不是用户的资金规模"。
提示词里写死一条：问到本金**必须**传进 `initial_cash`（只问不传等于没问）。

**刻意不做**：本金在对话侧是"必问"但不是"必填" —— 硬性 required 会让工具调用整体失败，
助手连"先问用户"那一轮都走不到。
