## 一、问题与目标

037 解决了三项**资金安全级**缺口(P0)。本轮处理六项**工程健壮级**缺口 —— 它们不直接吞钱, 但会让「回测说的」与「实盘兑现的」不一致, 或让故障无从发现:

| 代号 | 一句话 | 现状缺口 |
|:--|:--|:--|
| **P1-A** | 回测限价成交模型**去乐观** | 撮合是「bar 内价格**触及**限价 → 按限价 **100% 全成**」, 忽略排队位置。**旗舰网格策略正吃这个亏** → 回测收益被**系统性高估** |
| **P1-B** | Prometheus `/metrics` 只读端点 | **零**监控对接(`grep` 无命中); 外部系统看不到实例数/tick/挂单/持仓/权益/对账修正/拒单 |
| **P1-C** | 崩溃自动重启 | daemon 只记台账、**不重启**; 7×24 实盘下进程一挂就彻底停 |
| **P1-D** | 数据缺口检测 | 回测拉完 K 线**不校验时间连续性**, 缺口被**静默**喂给策略(指标算错却不报警) |
| **P1-E** | 实盘/回测对齐工具 | 无法拿同窗口实盘结果对比回测 —— 这是发现 P1-A 那类模型误差的**唯一实用手段** |
| **P1-F** | 下单延迟度量 | 不采集 `place_order` REST 往返耗时; 滑点模型缺真实依据、卡顿无从发现 |

**共同目标**: 让「回测可信 + 故障可见 + 运维可持续」, 且**默认行为尽量不变**(全部 opt-in 或纯新增)。

## 二、需求与验收

### FR-1 回测限价成交模型去乐观 (P1-A)

- **FR-1.1** 新增回测参数 `limit_fill_penetration_bps`(三层配置: 内置默认 < 策略 TOML `[backtest]` < CLI `--limit-fill-penetration-bps`), **内置默认 `0` = 保持既有行为**。
- **FR-1.2** 语义: 值 `N > 0` 时, 限价单需 bar **穿透**限价 `N` bps 才算成交 ——
  买: `bar.low <= limit × (1 − N/10000)`; 卖: `bar.high >= limit × (1 + N/10000)`。成交价仍为 `limit`(不给额外优惠, 不在无 tick 数据时伪造滑点)。
- **FR-1.3** 回测报告**单列**「限价单成交笔数 / 占全部成交比 + 穿透假设」, 让用户看见假设的影响。
- **FR-1.4** 默认值下(0 bps)**既有回测数字一字不变** —— 这是硬验收。

### FR-2 Prometheus `/metrics` 只读端点 (P1-B)

- **FR-2.1** 在**既有** web 服务上挂 `GET /metrics`(text/plain; version=0.0.4 暴露格式), **不开新端口、不引第三方依赖、不引云端**。
- **FR-2.2** 指标(全部**只读**、来自本地库与台账, **不直连交易所**):
  实例数(按状态) / 各实例挂单数 / 持仓数 / 权益 / 对账修正累计 / 拒单累计 / 回测作业数。
- **FR-2.3** 走**既有 token 中间件**(与其它端点同口径): 无 token 一律 `401` 空体。**不新增放行口**。
- **FR-2.4** **零写路径**: 该端点不读密钥、不落盘、不触发任何动作。

### FR-3 崩溃自动重启 (P1-C)

- **FR-3.1** daemon 新增 `[supervisor]` 配置段(`ricow.toml`): `restart_policy`(`none` 默认 / `on-failure`)、`max_retries`(默认 3)、`backoff_secs`(默认 5, 线性退避 ×重试次数)。
- **FR-3.2** **默认 `none` = 行为与现状完全一致**(零破坏)。
- **FR-3.3** `on-failure` 且**非主动停机**(`stop_all` 摘除的实例不重启)且退出码 ≠ 0 且未超 `max_retries` → 重启; 重启前**必须先走 037 P0-A 的挂单接管**(天然满足: 接管在策略进程启动段, 由子进程自己执行)。
- **FR-3.4** 重启事件如实落**台账**(`last_reason` 注明"自动重启 #N")与日志; 超限后**停止重启**并注明"已达最大重试次数, 需人工介入"。
- **FR-3.5** live 模式重启**不绕过确认面**: 子进程仍走既有 daemon 注入标记(`RICOW_DAEMON_SPAWNED`)路径, 语义与手动启动一致。

### FR-4 数据缺口检测 (P1-D)

- **FR-4.1** 新增纯函数(绑定层, `ricow_strategy`): 按 `interval` 推定期望 bar 步长, 扫描 K 线序列的时间连续性, 返回缺口清单(`缺口根数 + 缺口起止时刻`)。
- **FR-4.2** 在回测**取数完成后、喂引擎之前**校验: 存在缺口即**硬报错**(与既有"预热不足硬报错"同口径), 错误信息含**缺口数量 + 前若干处缺口的具体时刻与缺失根数**。
- **FR-4.3** **不静默降级**: 不提供"容忍缺口继续跑"的静默开关(与项目纪律"错误必须暴露"一致)。
- **FR-4.4** 只作用于**回测取数路径**; 不改变实盘行情流语义。

### FR-5 实盘/回测对齐工具 (P1-E)

- **FR-5.1** 新增只读 CLI 命令 `ricow align <策略名> [--card <run card 路径>] [--limit N]`: 取一份 run card(默认**最新**), 用其窗口 + 交易对 + 模式, 与本地 `fills` 表**同窗口实盘成交**对比。
- **FR-5.2** 输出逐项对照表(回测 vs 实盘 + 偏差): 成交笔数 / 成交名义 / 手续费 / 净现金流。
- **FR-5.3** **诚实性硬约束**: ①两侧口径差异必须**显式注明**(回测是虚拟撮合、实盘含真实滑点与部分成交, 且滑点/费率假设来自参数而非实测); ②实盘侧样本不足(如 0 笔)时**如实说"样本不足, 无从对比"**, 不给看起来完整的假结论; ③期货侧净现金流不是盈亏(需持仓与资金费), **标注为"现金净流入"而非"盈亏"**。
- **FR-5.4** 无写动作、无新确认面。

### FR-6 下单延迟度量 (P1-F)

- **FR-6.1** 引擎在每次 `ctx.place_order`(含策略单与停机清理单)前后计时, 采集**单次 REST 往返耗时**(微秒)。
- **FR-6.2** 收尾输出 `count / P50 / P95 / P99 / max`(微秒→毫秒展示), 计入 `RunOutcome` 并**随实例收尾日志打印**。
- **FR-6.3** **不改 `RunEvent` 字段与 schema 版本**(037 已确立事件 schema 冻结): 延迟只进 `RunOutcome` + 日志。
- **FR-6.4** 失败(传输错误)的调用**同样计入**耗时样本(那是真实的等待成本)。
- **FR-6.5** 无样本时**不输出统计行**(不给 "P50 = 0" 这种假数字)。

## 三、明确不做(本轮)

| 项 | 理由 |
|:--|:--|
| **P0-D 单笔名义上限 / 异常速率熔断** | 需**可配置风险参数面**, 与宪法 D15/D17 冲突, 属宪法级决策 —— 仍待用户拍板(见 `specs/roadmap.md` "下一步") |
| P1-A 引入 tick 级撮合 / 成交概率模型 | 需数据资产, 与项目"不做 tick 级回测"的定位冲突; 本轮只做 bps 穿透这一轻量杠杆 |
| P1-C 重启策略做成 per-instance 配置 | YAGNI: daemon 级一处即可; 每实例配置会再生一个配置面 |
| P1-B 引入 `prometheus` crate | 暴露格式简单到手写即可, 引入依赖不划算(宪法"少而精") |
| P1-E 自动跑回测再对比 | 对齐工具是**只读比对**, 自动跑回测会引入写路径与不确定性; 让用户先跑回测再对齐 |

## 四、验收口径

- **纯逻辑单测**: P1-A 穿透判定 / P1-D 缺口扫描 / P1-F 分位数 / P1-E 实盘事实汇总与渲染 / P1-C 重启决策 —— 全部为不依赖 IO 与交易所的纯函数, 各配单测。
- **既有回归**: `cargo test --workspace --no-fail-fast` 全绿, **基线不减**(起点 761 passed / 22 ignored / 0 failed)。
- **零行为变更验收**: P1-A 默认值与 P1-C 默认策略下, **既有回测数字与既有 CLI 文案一字不变**。
- **门禁五件**: `fmt --check` / `clippy --workspace --all-targets -D warnings` / `cargo deny --locked check` / `ci_grep_gates.sh` 五红线 / `architecture_guard` 三条。
- **真机冒烟**: `ricow align` / `ricow exposure` / `GET /metrics` 走临时数据目录端到端验证(不涉 testnet 下单)。

## 五、风险与回滚

| 风险 | 处置 |
|:--|:--|
| P1-A 默认口径被误改成非 0 → 既有回测数字漂移 | 内置默认硬编码 `0`; 单测直接断言「默认参数下 `try_match_ohlc` 行为与旧实现逐位一致」 |
| P1-D 硬报错让原本能跑的回测失败 | 这是**期望行为**(喂残缺数据算指标是更坏的结果); 错误信息给出缺口明细, 用户可缩短窗口或换 interval |
| P1-C 自动重启放大故障(反复崩溃 → 反复下单) | 默认 `none`; `on-failure` 有 `max_retries` 上限 + 退避; 每次重启都走 P0-A 挂单接管; 台账如实记 |
| P1-B `/metrics` 成为信息泄露面 | 与全部端点同一 token 门; 只暴露本地聚合计数, 不含密钥/单号/策略源码 |
| P1-E 给出误导性对比 | FR-5.3 三条诚实性硬约束: 注明口径差异 / 样本不足如实说 / 期货不把现金流叫盈亏 |
| P1-F 计时掩盖真实瓶颈 | 只报 REST 往返; 文档注明不含行情延迟与策略计算耗时 |
