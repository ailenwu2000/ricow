# 026 功能规格: 交易信息与日志可见性(成交/持仓回流 · Web 交易面板与日志流 · PnL 快照)

**状态**: 草稿 (2026-09-19) | **依据**: 用户四条质疑的取证结论 + 四项已拍板决策(D1–D4) + `specs/constitution.md`「完全本地化 / 少而精 YAGNI / 测试纪律」

## 一、为什么

用户跑完测试网后提了四个问题, 取证结论是: **交易在发生, 但没有任何一条通道把"发生了什么"送到用户和 AI 面前**。

四条断链(均已定位到代码):

1. **AI 会话对成交失明**。会话的执行结果只调 `sink.notice(&msg)` 显示一行 —— 这一行**不进** `ChatSession.history`(见 [session.rs](../../../crates/ricow/src/ai/session.rs#L312-L316))。模型看不到自己刚触发的动作成没成、成交没成交, 下一轮只能凭猜。用户问"刚才那单成了吗", 模型没有任何工具能查。
2. **Web 对交易与日志双盲**。Web 路由表只有 会话 / 术语 / 语言 三类端点([web/mod.rs](../../../crates/ricow/src/web/mod.rs#L196-L216)), 没有任何成交 / 持仓 / 日志端点; 页面上也就没有这些视图。
3. **交易数据本身不成形**。8 张表里只有 `fills` 一张交易流水表([db.rs](../../../crates/ricow_strategy/src/db.rs#L56-L195)), **没有 orders / 没有 positions**; `pnl_snapshots` 是**死表** —— 全仓除 `CREATE TABLE` 外无写入者、无读取者。
4. **日志一直在, 只是没人看得到**。策略子进程的 stdout/stderr 被重定向到 `logs/<name>.log`([procs.rs](../../../crates/ricow/src/supervisor/procs.rs#L62-L80), 10MB 轮转为 `.log.1`), tracing 只写 stderr 无文件层 —— 所以日志**不是没有**, 而是只有去翻文件才看得到。

对金融交易系统, 这四条合起来的后果是: 用户无法在界面或对话里确认"策略真的在交易"、"刚才那笔成交价格多少"、"风控行有没有报过警"、"这笔交易的盈亏是多少"。这正是用户原话"对于金融交易来说, 这个是很重要的"。

本次变更的主旨: **把已经存在的事实, 送到用户和 AI 面前** —— 新增落库使事实成形, 新增通道使事实可见, 且**不改任何执行语义**(下单/风控/确认门禁一行不动)。

## 二、范围

**做**:

- **交易落库**: 新增 `orders` / `positions` 两张表(幂等追加), 引擎在下单提交 / 成交回报 / 订单状态变化 / 持仓变化 时写入。
- **PnL 快照**: 让 `pnl_snapshots` 从死表变活表 —— 每笔成交后写一条快照, 永久保留。
- **Web 交易面板**: 新增只读端点(成交 / 挂单 / 持仓 / PnL), 页面新增交易面板。
- **Web 日志流**: 尾读 `logs/<name>.log`(先给最近 N 行)+ SSE 增量推送新行。
- **AI 会话回流**: 新增只读工具(查成交 / 持仓 / 挂单 / PnL / 读日志); 写动作确认执行后把**真实结果注入 history**, 修掉断链 1。
- **已覆盖项(本变更开工前已修, 记入本档案并待端到端验证)**: 「已停止」假阴性(daemon 连不上被说成"已经停着")与测试网印「实盘停机」文案 —— 两条已改完, 本次只做端到端复验, 不重复改。

**不做**:

- **不直连交易所取数**(D1): 面板与 AI 一律读本地库, Web 层不引入交易客户端、不引入第二套行情/账户查询路径。
- **不做运行中主动推送**(D4): 策略进程一有成交就主动推给会话的能力**不在本次范围** —— 需要跨进程事件通道, 留待后续变更。本次只做"查得到"+"确认执行后看得到"。
- **不改任何执行语义**: 下单 / 撤单 / 风控 / 平仓 / Dry Run 撮合 / 确认状态机 / tty 门禁 / 15 分钟 pending TTL —— 一行不动。本次只加"记账"与"呈现"。
- **不改 `fills` 表语义**: 它仍是唯一成交流水表, 不新增第二张成交表。
- **不做日志结构化**: 日志按原样呈现, 不解析、不做关键字着色猜测(沿用 025 的"级别由宿主显式标注"原则); `.log.1` 轮转文件**不在本次范围**(面板只读当前日志文件, 与 CLI 看当前文件同口径)。
- **不引入前端构建链**(沿用 025 D4): 手写静态资源 + `include_str!` 内嵌, 无 npm / 无打包器。
- **不做图表可视化**: 不做 K 线图 / 不做资金曲线绘制(只给 PnL 数据点)。
- **不改既有 CLI 用户可见文案**: `ricow fills` / `ricow info` / `ricow logs` 等输出逐字保留。
- **不做日志云同步 / 上传 / 导出**。

## 三、功能需求

### 交易落库(F0)

- **FR-001**: `db.rs` 的 `migrate()` 以 `CREATE TABLE IF NOT EXISTS` **幂等**追加 `orders` 表, 至少含: `strategy_id` / `exchange_order_id` / `client_order_id` / `pair` / `side` / `price` / `size` / `filled_size` / `status` / `created_at` / `updated_at`; 既有 8 张表结构零改动。
- **FR-002**: 同法追加 `positions` 表, 至少含: `strategy_id` / `pair` / `size`(带方向) / `entry_price` / `updated_at`; 每策略每交易对**一行**(主键 `strategy_id` + `pair`), 表示**当前**持仓, 不是流水。
- **FR-003**: 引擎在四个时点把最新状态 upsert 入库: **下单提交** / **成交回报** / **订单状态变化** / **持仓变化**。
- **FR-004**: 落库失败**不得中断交易主流程**: 写库错误只记日志并继续, 不得向上抛出改变执行结果。
- **FR-005**: 三种运行模式(`dry_run` / `demo` / `live`)的数据**必须可区分** —— **新增的** `orders` / `positions` 记录带模式标识(不在 `fills` 表加列, 见 FR-001); 成交的模式由 `exchange_order_id` 关联 `orders` 带出; 关联不到时**如实**显示"未知", 不猜。
- **FR-006**: 落库的 `strategy_id` 口径与既有 `fills` 写入一致(同一策略在四张表里是同名)。

### PnL 快照(F1)

- **FR-007**: 每笔成交落库成功后写一条 `pnl_snapshots`(`strategy_id` / `timestamp` / `realized_pnl` / `fees` / `net_pnl` / `trade_count`); **不改该表列结构**。
- **FR-008**: 快照数值与策略侧 `ctx:net_pnl()` / 既有 `fill_stats` **同源同口径**, 不在 Web 或 AI 侧重算第二套。
- **FR-009**: 快照**永久保留**: 不做 TTL、不做行数淘汰。

### Web 交易面板(F2)

- **FR-010**: 新增只读端点: 成交列表(支持按策略过滤 + `limit`)、持仓、挂单、PnL 数据点。
- **FR-011**: 全部新端点走既有 token 中间件(缺失 / 错误 token 一律 `401` 且响应体为空), 服务仍只绑 `127.0.0.1`。
- **FR-012**: 页面新增交易面板: 展示当前持仓 + 挂单 + 最近成交; 数据来自 FR-010 端点。
- **FR-013**: 面板是**只读**的: 页面不提供直连交易所的按钮; 任何写动作(撤单 / 平仓 / 停机)仍必须走既有对话确认流程。
- **FR-014**: 空状态**如实**呈现: "无持仓"、"无成交"、"daemon 未运行, 此刻状态不可知"三种必须分开, 不得把"读不到"说成"没有"(假阴性)。

### Web 日志流(F3)

- **FR-015**: 新增日志端点: 返回指定策略 `logs/<name>.log` 的最近 N 行; N 有**硬上限**, 请求超大 N 时被夹到上限(不返回整个文件)。
- **FR-016**: 新增日志 SSE 流: 服务端尾读该文件, 新增行**实时**推给页面; 页面刷新后重建。
- **FR-017**: 日志面板可切换策略; **策略未运行时仍可看历史日志**(文件在就该看得到)。
- **FR-018**: 日志内容**原样**呈现: 不解析、不改写、不做关键字级别的着色推断。

### AI 会话回流(F4)

- **FR-019**: 补齐**只读工具**的缺口: "查成交 / 读日志"两个**已存在**(`fills` / `logs_tail`, 白名单 12 项), 本次**不改其行为**; 新增"查持仓 / 查挂单 / 查 PnL"三个(带策略名与条数上限)。只读工具不需要确认(沿用宪法"只读动作不需确认")。
- **FR-020**: 只读工具的返回必须**区分**"确实没有"与"读不到": daemon 未运行 / 库不可读时如实说"无法判断", 不得假阴性地说"没有"。
- **FR-021**: 写动作**确认执行后**, 把真实执行结果**注入 `ChatSession.history`**, 使模型在下一轮能看到自己动作的结果。
- **FR-022**: 注入 history 的内容与 `sink` 显示的内容**同源**(不得存在两条文案); 注入**不得**改变确认状态机语义(确认词仍只认真实用户输入行)。
- **FR-023**: 注入内容按既有 `clip_for_history` 上限裁剪, 保证不撑爆 token。
- **FR-024**: **失败结果同样注入**(模型必须知道动作失败了, 而不是以为成功)。

### 零回归(F5)

- **FR-025**: 既有 CLI 用户可见行为**零变化**: `ricow fills` / `ricow info` / `ricow logs` / `ricow daemon *` / `ricow start|stop` 等输出文案与退出码不变。
- **FR-026**: 025 的 Web 能力零回归: 会话 CRUD / SSE 会话帧 / 术语 / 语言端点的契约与页面行为不变。
- **FR-027**: 旧库兼容: 用**不含新表**的既有数据库文件打开 → 自动补齐新表, 既有表数据逐行不变(迁移幂等)。
- **FR-028**: 落库与可见性新增逻辑不得让交易主流程的通路变慢或变脆: 新增写库不得进入下单 / 风控的关键路径的阻塞等待。

## 四、验收标准

- **SC-001**: `cargo fmt --all -- --check` 零差异、`cargo clippy --workspace --all-targets --locked -- -D warnings` 零警告、`cargo test --workspace --locked` 全绿; 基线 **480 passed / 0 failed / 21 ignored** 不得倒退。
- **SC-002**: 端到端(真实调用, 禁 mock): 跑一次 demo 测试网策略 → 产生**真实成交** → 在 Web 交易面板上**页面上**看到该笔成交与持仓; 同时 `logs/<name>.log` 的新行**实时**出现在日志面板。全程无终端交互。
- **SC-003**: 落库单测: 下单 → 成交 → 持仓变化后, `orders` / `positions` / `fills` / `pnl_snapshots` 四表的行与数值符合预期; 注入写库错误后**交易主流程仍继续**(FR-004)。
- **SC-004**: 幂等迁移: 用旧版数据库文件(不含新表)打开 → 自动补齐 `orders` / `positions`; 既有 8 张表数据逐行不变。
- **SC-005**: AI 回流: 写动作确认执行后, 下一轮模型可见该结果 —— 断言 `history` 中含该结果文案, 且与 `sink` 显示**同源**; 失败场景同样注入。
- **SC-006**: 只读工具无假阴性: daemon 未运行时查持仓 → 返回"无法判断"而非"没有持仓"; 确实无持仓时才说"无"。
- **SC-007**: 只读端点鉴权: 无 token / 错 token 请求返回 `401` 且响应体不含任何交易数据。
- **SC-008**: 日志端点有上限: 请求超大 N 时响应行数被夹到上限。
- **SC-009**: 零回归: `git diff` 中既有 CLI 用户可见文案与 025 的 Web 端点契约**无改动**。
- **SC-010**: 文档同步: `specs/architecture.md` 补交易落库与可见性章节(表清单从 8 张更新为 10 张), `specs/roadmap.md` 记录本变更。

## 五、已拍板决策

- **D1 — 数据以**本地库**为准**: 面板与 AI 一律读本地 SQLite, **不直连交易所**。理由: 离线可看、与策略进程解耦、查询快; 代价 = 与交易所瞬时状态可能有延迟差, 由用户接受(§六)。
- **D2 — 日志用**尾读 + SSE 增量推送**: 打开先给最近 N 行, 之后新行实时推; 复用 025 既有 SSE 通道。理由: 对金融交易, 成交 / 撤单 / 风控行**当场可见**比"手动刷新"有用得多。
- **D3 — PnL 快照 = 每笔成交后一条 + 永久保留**: 成交是唯一让 PnL 变化的事件, 一笔一条够用且不冗余; 永久保留便于回看整条曲线。
- **D4 — AI 回流 = 只读工具 + 执行结果注入 history**: 先修"模型失明"这条断链; **不做**运行中主动推送(需跨进程事件通道, 留后续变更)。

## 六、假设

- 引擎与策略进程在**同一数据目录**下工作, 交易库与既有行情库是同一个 `Database` 实例 / 同一文件。
- 交易落库属**低频写**(每笔成交 / 每次状态变化一行), SQLite WAL 足以支撑, 不引入额外队列。
- 用户接受 D1 的代价: 面板以本地库为准, 可能与交易所瞬时状态存在延迟差; 需要绝对实时时仍以交易所界面为准。
- 日志为**纯文本追加**、行内无结构化级别 —— 故 D2 只做原样呈现, 不做着色推断。
- Web 前端不参与策略执行, 仅作**只读视图 + 对话前端**; 新增面板不复制任何业务逻辑。
- 本次不含「已停止」假阴性与「实盘停机」文案的**代码改动**(开工前已修完), 只做端到端复验。
